# Phase 4 — Media layer

Goal: images and WebM video actually decode, display, and play smoothly, with
a concrete tested definition of "supported" rather than "every extension we
found." Corresponds to overview sections 8 and 9.

## Supported-format definition

- [x] Concrete list of supported image formats: `.jpg`/`.jpeg`, `.png`,
      `.gif`, `.bmp`, `.webp`, `.tif`/`.tiff` (`media/formats.py`) — the
      conventional raster photo/collection formats, cross-checked against
      `QImageReader.supportedImageFormats()` in this Qt build rather than
      assumed (`tests/unit/media/test_formats.py`). Qt's build also exposes
      plugins for icons, cursors, PDF, and vector/XPM formats that were
      deliberately left out as inappropriate for a media collection.
- [x] WebM video support defined by the actual codecs the chosen playback
      stack provides, validated against fixtures — see the important finding
      below; this was **not** what the obvious API suggested.
- [x] Audio accompanying supported video plays when present — verified via
      an audio-bearing WebM fixture reporting a decoded audio track and no
      error (`tests/unit/media/test_video.py`); actually *hearing* it isn't
      something an automated test can assert without real audio-output
      hardware capture, so "a track is present and playback reaches
      end-of-media with no error" is the practical proxy used here.
- [x] Extension is only a candidate filter (used by the Phase 2 scanner) —
      actual decoding is what determines validity here (`media/image.py`,
      `media/video.py`)
- [x] Animated-image behavior isn't separately promised or tested this
      phase — the overview only requires documenting it "as whatever the
      chosen Qt stack does," and nothing in the v1 feature set (section 2)
      calls for animation playback specifically; revisit if/when Phase 5's
      viewer needs it.

## Important finding: Qt Multimedia's default backend can't play WebM

`QMediaFormat`'s static capability query (`supportedVideoCodecs`/
`supportedAudioCodecs`) reports **no** VP8, VP9, Opus, or Vorbis support at
all in this Qt 6.11 / PySide6 build, on *either* of its two bundled
backends. Taken at face value, that would mean WebM — a **required** format
per the overview — doesn't work here.

Actually playing the generated fixtures through a real `QMediaPlayer` told
a different story:

- The **"windows"** backend (Windows Media Foundation) genuinely can't play
  the WebM/VP9 fixture: `mediaStatusChanged` goes straight to
  `InvalidMedia` and `errorOccurred` fires `ResourceError: Unable to play.`
  This matches the capability query — WMF has no VP8/VP9/Opus/Vorbis
  decoders.
- The **"ffmpeg"** backend plays both the video-only and audio-bearing WebM
  fixtures correctly — reaches `EndOfMedia`, correct duration, audio and
  video tracks both present, no error at all. The static capability query
  was simply wrong/incomplete for this backend; its real decode capability
  comes from the bundled FFmpeg libraries, not the enum Qt exposes.

This build's *default* backend already happens to be `"ffmpeg"` (Qt 6.8+
made it the cross-platform default), which is why the very first fixture
test passed before this was investigated further. That default isn't
pinned anywhere, though, and WebM is a required feature — so
`bootstrap.py` now sets `QT_MEDIA_BACKEND=ffmpeg` explicitly before any
multimedia object is constructed, rather than relying on an undocumented
default that could change with a Qt upgrade or a different install.
**Takeaway for future sessions:** don't trust `QMediaFormat`'s codec enum
for this backend — validate against real fixture playback instead, exactly
as this phase's checklist already said to.

## Test fixtures (`tests/fixtures/media/`)

Generated by [`tools/generate_media_fixtures.py`](../../../tools/generate_media_fixtures.py)
(rerun it if a fixture needs to change — the outputs are committed, so
tests never need to regenerate them). Images are authored directly with Qt
(`QImage`/`QPainter`); WebM files are authored with a real `ffmpeg` binary
from the `imageio-ffmpeg` dev dependency (a fixture-authoring tool only,
never a runtime dependency of the app itself).

- [x] Supported image (`supported_image.png`, 64×64)
- [x] Large image (`large_image.png`, 3000×2000 with a gradient + grid so
      it isn't trivially flat, for downsample/cache testing)
- [x] Corrupt image (`corrupt_image.jpg` — garbage bytes with a `.jpg`
      extension)
- [x] Supported WebM (`supported_video.webm` — VP9 profile 0/yuv420p, no
      audio; explicit `-pix_fmt yuv420p` after profile-1/gbrp from
      ffmpeg's `testsrc` default turned out to matter for compatibility)
- [x] Audio-bearing WebM (`audio_video.webm` — VP9 + Opus)
- [x] Unsupported media: `unsupported.txt` (extension not a candidate at
      all) and `corrupt_video.webm` (a `.webm` extension, invalid content —
      added for symmetry with the corrupt image fixture, to exercise
      `VideoPlayer`'s error path the same way)

## Loading (`media/loader.py`, `media/image.py`, `media/video.py`)

- [x] Image decode path (`media/image.py::load_image`) — a pure function,
      no threading of its own; safe to call off the GUI thread by the
      caller (Phase 3's `WorkerPool`, once Phase 5 wires it up)
- [x] Video load/playback path via `QMediaPlayer`/`QAudioOutput`
      (`media/video.py::VideoPlayer`)
- [x] Corrupt/invalid media surfaces as a handled error state, not a crash
      — `QImage` doesn't raise on bad content, it returns a null image
      (`isNull()`), turned into `ImageLoadError`; `QMediaPlayer` emits
      `errorOccurred`, re-surfaced as `VideoPlayer.load_failed`
- [x] Every load/decode/preload request carries a generation/request id —
      for **images** (`ImageLoader.begin_request()`/`load()`/`preload()`).
      **Video deliberately doesn't get its own generation counter**: a
      `VideoPlayer` represents one live, replaceable player object, and
      `QMediaPlayer.setSource()` already supersedes whatever it was
      previously loading at the Qt level — there's no async decode *result*
      that could resolve out of order the way image loads can. Documented
      in `media/video.py`'s module docstring so it doesn't look like an
      oversight.

## Caching (`media/cache.py`)

- [x] Bounded cache — `ImageCache` evicts least-recently-used entries once
      a byte budget (`QImage.sizeInBytes()`-based, not item count) is
      exceeded
- [x] Appropriate downsampling for display size — `image.py::downsample`
      scales to fit within a max dimension, never upscales
- [x] Eviction of obsolete decoded data — LRU eviction in `ImageCache`
- [x] Preloading of likely-next items without unbounded memory growth —
      `ImageLoader.preload()` warms the cache; the same byte-budget
      eviction bounds it regardless of how many paths get preloaded

**Design simplification, worth knowing about later:** `ImageLoader` only
ever caches the *downsampled* image, never the full original decode — so
large images are never retained at full resolution at all once loaded here,
which trivially satisfies "not retained indefinitely at full resolution."
The tradeoff: if Phase 5's viewer ever needs full-resolution pixel data
(e.g. zooming in past `max_display_dimension`), that's a fresh re-decode,
not a second cache tier. Not built ahead of an actual Phase 5 requirement
for it — revisit if/when zoom needs it.

## Staleness under rapid navigation

- [x] Stale decode/load results are discarded before they can replace the
      currently displayed media — `ImageLoader.load()` rechecks staleness
      both before *and* after the decode itself (decoding a large image can
      take long enough for a newer request to have superseded it mid-flight)
- [x] Rapid back-to-back navigation does not cause flicker to a
      previously-requested (now stale) item — a burst of five requests
      against the same loader, only the last one ever returns non-`None`
